# 工單延遲風險預測模組（ML）— 規劃與實作紀錄 v1

> **先講最重要的一件事：訓練資料是模擬的，不是真實產線資料。**
>
> 生成規則是我自己寫的（`HistoricalWorkOrderGenerator`），所以模型學得回那條規則
> 幾乎是必然的 —— 它證明的是「整條 pipeline 接起來了、而且每個決策講得清楚」，
> **不是**「這個模型對真實產線有效」。真實資料的訊號會弱得多，雜訊也不是這種長相。
>
> 這句話放在最前面而不是附註裡，因為整個模組的可信度建立在它上面。
> 拿一份來路不明的資料集套一個 0.99 的模型、再宣稱它能預測產線，
> 比誠實標明「這是模擬的」要糟得多。

## 1. 這個模組要證明什麼

ERP 已經有一套規則式的工單風險判定（`WorkOrderRiskService`：逾期 + 缺料兩種來源）。
它可解釋、上線不需要任何歷史資料，而且現在就在跑。那為什麼還要一個模型？

因為兩者回答的不是同一個問題：

| | 規則式 | 模型式 |
|---|---|---|
| 回答 | 這張工單**為什麼**有風險 | 這張工單**多可能**延遲 |
| 依據 | 寫死的兩條規則 | 七個特徵的加權組合 |
| 需要歷史資料 | 不需要 | 需要 |
| 說得出理由 | 說得出（逾期幾天、缺哪個料） | 說不出 |
| 抓得到規則沒寫的組合 | 抓不到 | 抓得到 |

現場要的是「為什麼」，管理要的是「哪幾張最該先看」。只留一個都會是錯的答案，
所以這個模組的落地方式是**並存**：`predict_work_order_delay_risk` 這個 AI 工具
同時回傳兩邊的結果，並在 `note` 裡講明差異。

## 2. 範疇界定

**不做**：深度學習、大規模資料集、線上重訓、模型監控與自動退版。
資料量小的情況下做這些不會更真實，只會更像在演。
線上重訓尤其：一張工單要等到完工才知道有沒有延遲（標籤延遲），
資料回流、標籤補齊、模型版本管理每一項都是獨立的工程，做半套是假的。

**做**：一條完整、誠實、每個決策都講得出理由的傳統 ML pipeline ——
資料生成 → 清理 → 特徵工程 → 訓練 → 評估 → 閾值選擇 → 落地成一個與規則式並存的服務。

## 3. 資料

`HistoricalWorkOrderGenerator` 產生 1200 筆模擬歷史工單，固定亂數種子（20260913），
所以同一個 seed 產生的資料完全一樣 —— 這是「clone 下來能訓練出同一個模型」的前提。

延遲機率的生成規則：

```
logit = -1.2
      + 2.8 × (1 − 齊套率)                 缺料是最強的訊號
      + 0.18 × max(0, 前置期 − 剩餘天數)     補得上就不算風險
      + 1.1 × max(0, 負載 − 1)              超過基準負載才開始拖累
      + 1.5 × 品項逾期比例
      − 1.6 × 完成比例                      做得越完整越不會延
      − 0.05 × 剩餘天數
```

取 sigmoid 當延遲機率，抽一次伯努利。延遲比例 46.5%（兩個類別都有足夠樣本，
不平衡到某一類只剩幾十筆的話，模型只要全猜多數類就有高準確率，評估數字會失去意義）。

**刻意加進去的髒東西**，讓「資料清理」這一步真的有事可做：

| 雜訊 | 比例 | 對應的現實情境 |
|---|---|---|
| 標籤翻轉 | 5% | 現場登錄錯誤；或延遲原因與工單無關（颱風、客戶改單） |
| 齊套率缺值 | 8% | 舊系統沒有這個欄位 |
| 當週負載缺值 | 6% | 同上 |
| 負載離群值（× 8~15） | 1.5% | 盤點當天把整月工單一次開出來造成的假尖峰 |

缺值在 CSV 裡是**空字串**而不是 0 或 −1：用哨兵值代表缺值的話，
模型會把那個數字當成真的量測結果來學。這條有測試釘住。

**資料生成寫在 C# 而不是訓練腳本裡**，理由見第 6 節。

## 4. 資料清理 —— 每個決定都要說得出為什麼選這個

### 缺值：中位數補值，不刪樣本，也不加缺值旗標

刪樣本：齊套率缺 8.9%，刪掉會連帶丟掉那些列其他欄位的資訊，代價太高。

加 `is_missing` 旗標（通常比補值更好的做法）：**這裡刻意不做**，
因為線上推論時這兩個欄位一定算得出來 —— 系統有 BOM、庫存與工單，齊套率不會缺。
缺值只存在於歷史資料。加旗標等於製造一個線上永遠是 0 的特徵，
模型會學到一個上線後不存在的訊號。

實際補了：齊套率 107 筆（中位數 0.5854）、當週負載 65 筆（中位數 1.0387）。

### 離群值：IQR 上界夾住（winsorize），不刪樣本

那些列的其他欄位仍然是有效資料，而且「負載很高」本身是真的，只是高得不合理。
實際夾了 19 筆，上界 2.0896。

## 5. 特徵工程

最後採用七個：

| 特徵 | 定義 | 為什麼 |
|---|---|---|
| `material_readiness` | 缺料件中覆蓋率**最低**的那一件 | 最嚴重的那個決定整張工單做不做得出來；取平均會被齊全的料稀釋掉 |
| `days_until_due` | 交期 − 今天，**已逾期是負數** | 逾期程度本身就是訊號，夾成 0 等於把「逾期三天」與「今天到期」當成同一件事 |
| `max_lead_time_days` | 缺料件中最長的採購前置期 | 決定「補不補得上」 |
| `progress_ratio` | 途程最後一站完工數 ÷ 計畫產量 | 做得越完整越不會延 |
| `item_overdue_rate` | 該品項未結案工單中已逾交期的比例 | 品項本身的體質 |
| `weekly_load_ratio` | 交期當週未結案工單數 ÷ 產線基準 | 產線塞不塞得下 |
| `bom_component_count` | BOM 展開後的葉節點原料件數 | 結構複雜度的代理變數 |

### 捨棄的候選 —— 這一節比上面那張表重要

**「歷史延遲率」：因為線上算不出來而換掉。**

第一版的特徵表裡有 `item_historical_delay_rate`（該品項過去實際延遲的比例）。
它的預測力比現在這個替代品好，離線評估也會更好看。寫到線上推論才發現：
**系統沒有記錄工單的實際完工日**，只有交期與狀態，所以「當初有沒有準時完工」
這件事在資料裡根本不存在。

這件事的教訓寫成一句話：**特徵工程的第一個判準是「預測當下拿不拿得到」，
不是「有沒有預測力」。** 一個離線算得出來、線上算不出來的特徵，
離線評估會很漂亮，上線就是空的。換成語意相近、而且現在就查得到的
「該品項未結案工單中已逾交期的比例」。

**與實際完工日相關的任何衍生欄位：data leakage。**
「實際完工日 − 交期」直接就是標籤本身。預測當下不知道的資訊不能當特徵，
這條沒有例外。

**工單建立者、客戶名稱：沒有因果、而且會在小樣本上過擬合。**
1200 筆資料配上高基數的類別欄位，模型會記住個別的人名而不是學到規律。

## 6. training/serving skew —— 三道防線

同一個特徵在訓練時與線上算得不一樣，是這類系統最典型、也最難查的失敗：
不會報錯，離線評估看不出來，線上算出來的機率卻是拿錯尺量的。三道防線：

### 6.1 特徵定義只有一份，而且在 C# 這一側

`WorkOrderDelayFeatures` 是唯一真相。訓練資料由它產生（`HistoricalWorkOrderGenerator`
輸出的 CSV 欄位順序直接來自 `FeatureNames`），線上推論也由它組出來。

這是「資料生成寫在 C# 而不是 Python」的理由：由 Python 生成的話，
「齊套率」會有兩個實作 —— 一個在訓練腳本、一個在線上推論 —— 兩邊差一點點就是 skew。
Python 只負責它真正擅長的事：訓練與評估。

### 6.2 黃金樣本

訓練時把七組測試集輸入與 sklearn 算出來的機率一起存進 metadata，
`DelayRiskModelTests` 驗 ONNX 載進 .NET 之後算出同一個數字（誤差 < 1e-6）。

它抓的是一個不會報錯的失敗：ONNX 吃的是沒有欄位名稱的張量，
特徵順序錯位、或機率取到第 0 欄（不延遲）而不是第 1 欄，推論都會照跑。
反向驗證：把 `ToVector` 的前兩個欄位對調 → **只有這一條會紅**；
把 `probabilities[0, 1]` 改成 `[0, 0]` → 紅 2 條。

### 6.3 端到端實跑（這一道抓到了一個真的 bug）

第一版的 `bom_component_count` 寫成「有缺料時用缺料件數、沒缺料時用葉節點數」。
單元測試全綠、離線評估正常，**端到端打一次 API 才看出來**：
展示工單的這個特徵是 1（缺料件數），而訓練資料裡它是 2~8（葉節點數）。
同一個特徵在兩種情況下代表不同的東西。

修正成一律用葉節點數，並補一條測試釘住「有沒有缺料，這個特徵都是同一個意思」。

## 7. 模型與訓練

**Logistic regression，不是 gradient boosting。** 1200 筆、7 個特徵的規模，
boosting 換來的額外表現，代價是「說不清楚為什麼」——
而這個模組的重點就是每個決策講得清楚。線性模型的係數本身就是說明。

`StandardScaler` 放進 pipeline 一起匯出，線上推論不必再標準化一次 ——
那是另一個 skew 的經典來源。

訓練/測試切分 75/25，`stratify` 保證兩邊的延遲比例一致
（否則測試集的基準率會漂，評估數字不能跟別次比較）。

## 8. 評估與閾值 —— 為什麼不是 0.5

2026-09-13 的實測（300 筆測試集）：

| 指標 | 值 |
|---|---|
| ROC AUC | 0.7386 |
| Average Precision | 0.6997 |
| 選定閾值 | **0.26** |
| 閾值 0.26 下 | precision 0.5605、recall 0.8993 |
| 對照閾值 0.5 | precision 0.6829、recall 0.6043 |
| 混淆矩陣（0.26） | TN=63、FP=98、FN=14、TP=125 |

**AUC 0.74 而不是 0.99，是這份資料誠實的結果**：生成規則裡有 5% 標籤翻轉，
而且延遲與否是從機率抽出來的伯努利，本來就不是可以完全預測的。
一個假到 0.99 的數字反而該懷疑。

**閾值 0.26 是選出來的，不是預設值。** 漏抓一張會延遲的工單（false negative）
的代價是客戶端的交期跳票；誤報（false positive）的代價只是生管多看一眼。
兩者不對稱，閾值就不該用對稱的 0.5。做法是掃過所有閾值，
挑「recall ≥ 0.85 的前提下 precision 最好的那個」。

代價講清楚：這個閾值下每抓到 125 張真的會延遲的工單，會誤報 98 張。
接不接受這個比例是業務判斷，不是技術判斷 —— 而模型該做的是把這個取捨攤開來讓人選，
不是替人選好。訓練腳本裡若沒有任何閾值達得到目標 recall，它會直接失敗並說
「該回頭看特徵而不是調閾值」。

## 9. 落地整合

- `IDelayRiskModel`（Application 的 port）／`OnnxDelayRiskModel`（Infrastructure 的實作）。
  推論用的 ONNX Runtime 是基礎設施細節，Application 不該知道模型用什麼跑
  —— 與 `ILlmClient`、`IEmbeddingClient` 同一條規則，由架構測試釘住。
- `WorkOrderDelayRiskPredictionService` 組合規則式與模型式，回傳兩者並陳。
- AI 工具 `predict_work_order_delay_risk`、HTTP 端點 `/api/work-orders/{no}/delay-risk`。
- **可選模組**：模型檔載不起來時整個服務照常啟動，`IsAvailable` 是 false，
  預測服務如實說「沒有模型」，而**不是回一個看起來像機率的預設值** ——
  那是最糟的失敗方式。與 RAG 同一個模式。
- 模型是離線訓練的靜態檔案，換模型就是換一個檔案、重跑 `ml/train.py`。

## 10. 校準與分布外檢查（2026-09-16 補做）

原本第 10 節把「沒有校準」與「沒有分布檢查」列為已知限制。這一輪把兩件事都處理掉了，
**但其中一件的結論是「不做」** —— 那不是逃避，是有數字支持的決定。
模型權重完全沒動（重跑後 ONNX 位元相同），變的是「模型對自己說了什麼」。

### 10.1 校準：評估過，不採用

機率校準要回答的是：模型輸出 0.68 時，這類工單真的有 68% 會延遲嗎？
這與 AUC 無關 —— 把所有機率開根號，AUC 一模一樣，校準卻全毀。

先驗上 logistic regression 不太需要校準（它最佳化的就是 log loss，輸出本來就接近校準過的機率），
但先驗不算數，所以真的跑了一次（300 筆測試集）：

| | Brier ↓ | ECE ↓ | ΔBrier 的 95% bootstrap 區間 |
|---|---|---|---|
| 未校準 | 0.20654 | 0.06567 | — |
| Platt（sigmoid） | 0.20609 | 0.05539 | [−0.0018, +0.0009] |
| isotonic | 0.20866 | 0.08243 | [−0.00123, +0.00567] |

**判準刻意不是「改善超過百分之幾」那種拍腦袋的門檻**，而是 bootstrap 重抽測試集 2000 次
算 ΔBrier 的 95% 區間：兩種方法都跨 0，也就是這 300 筆資料分不出校準前後的差別。
isotonic 甚至在點估計上更差（ECE 惡化 25%），那是小樣本上典型的過擬合。

結論：**不採用校準**。分不出差別時多一層轉換，只是多一個沒有證據支持的加工、
多一個要維護的東西。取而代之的是把這件事講出來 —— `IDelayRiskModel.IsCalibrated`
是 false，API 說明與 AI 工具描述都寫明「0.68 的意思是比 0.42 更值得先看，
不是六成八會延遲」。這個區別被混為一談的成本是錯誤的決策。

reliability 分箱的原始數字存在 metadata 的 `calibration.reliability_bins` 裡。
從那張表也看得出來為什麼差異分不出來：最高的那一箱只有 4 個樣本。

### 10.2 分布外（OOD）檢查：做了，而且第一個被標出來的就是展示資料

訓練時把每個特徵的 p1/p99 寫進 metadata（`feature_ranges`），
線上推論時比對，超界的特徵連同訓練範圍一起回報在 `outOfDistributionFeatures`。

**邊界取 p1/p99 而不是 min/max**：後者被單一一筆極端值決定，
線上只要有一張工單稍微超過那一筆，就會整批被標成分布外 ——
警告發久了沒人看，比不做還糟。

第一個被標出來的就是展示資料本身：`weekly_load_ratio` 是 0.125，訓練下界 0.5088。
也就是說**展示站上看到的每一個機率，都是模型對沒見過的輸入給出來的**。
這件事以前只寫在文件的已知限制裡，現在 API 回應會直接講，
`DemoEnvironmentTests` 有一條端到端測試釘住它。

**這裡抓到一個沒預料到的缺陷。** 第一版直接用 `<` / `>` 比大小，
結果訓練集裡的黃金樣本被標成分布外：特徵向量是 float32（ONNX 吃的型別），
邊界是 metadata 裡的 double，值剛好等於邊界的樣本轉成 float 之後變成
`0.11999999731779099`，比 `0.12` 小。修正是加一個與範圍成比例的容差
（`max(1e-6, (p99−p1) × 1e-6)`）。是「分布內的輸入不會被標成分布外」那條測試抓到的，
不是想出來的 —— 沒有那條反向對照，這個誤判會一路活到展示現場。

反向驗證：把邊界檢查整段拿掉 → Infrastructure 與 Api 各紅一條；
把 service 傳遞那行拿掉 → Application 紅一條；把 metadata 的 calibration 區塊刪掉 → 紅一條。

## 11. 仍然沒有的東西

- **訓練資料是模擬的。** 重複一次，因為它決定了其他所有數字怎麼被解讀。
- **沒有資料漂移監控、沒有重訓機制。** 模型檔是靜態的，線上輸入的分布變了不會有人通知你。
  規劃在 [`ml-dl-llm-strengthening-plan-v1.md`](ml-dl-llm-strengthening-plan-v1.md) 的 S5，
  MLflow 實驗追蹤與漂移偵測都還沒做——這部分等 S1/S2 有更多模型後再做才划算。
  已經做掉的是 S5 提到的另一半：**模型檔與程式碼版本對不上時能不能當場看出來**
  （2026-09-17）——`OnnxDelayRiskModel` 現在會比對 metadata 宣告的特徵順序跟
  `WorkOrderDelayFeatures.FeatureNames`，對不上就停用預測（不是照跑一個算錯的機率），
  `/api/ml/model-health` 把這個狀態（連同訓練日期、資料來源、樣本數、ROC AUC）
  直接曝露出來，不用另外開一個 MLflow 才看得到。
- **`WeeklyCapacityWorkOrders`（產線基準負載）是寫死的常數**，真實系統該從產能主檔取。
- **OOD 只看單一特徵的邊界**，看不到「每個特徵都在範圍內、但這個組合沒出現過」
  那種多維度的分布外。要抓那種需要密度估計或 Mahalanobis 距離，
  1200 筆、7 維的資料量做了不見得可靠，所以停在單變量。

## 12. 怎麼重跑

```bash
dotnet run --project tools/Erp.MlDataGen

# 二、訓練、評估、匯出 ONNX 與 metadata
python3 -m venv ml/.venv
ml/.venv/bin/pip install -r ml/requirements.txt
ml/.venv/bin/python ml/train.py
```

**推論不需要 Python。** 模型以 ONNX 格式進 repo，由 .NET 的
`Microsoft.ML.OnnxRuntime` 載入 —— clone 下來跑 `dotnet test` 不必裝任何 Python 套件。
只有「重新訓練」才需要上面第二步。
