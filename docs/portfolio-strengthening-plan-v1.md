# 作品集強化規劃 v1（2026-09-13）

## 目的與背景

這份文件是在 AI 助理模組（Phase 1-4）與 RAG 模組全部完成、CI 綠燈、README/文件也已完成求職語氣中性化之後，針對「這個專案接下來還能怎麼加強」做的一次盤點與重新規劃。

目前手上有兩條求職路線在同時進行：

1. **台中/中科 ERP、製造業 MIS 後端工程師**：這條路線這個專案已經對得很齊（ASP.NET Core Web API、EF Core、Clean Architecture、BOM/工單/採購/品檢的業務邏輯、xUnit 測試、CI），落差不大。
2. **AI 工程師職缺（104 job/92xef）**：JD 明確寫的是「在資深工程師指導下開發/部署 AI 模型、ML/DL/NLP、大型資料集分析、資料清理與特徵工程、跨部門協作、LLM 微調與生成式 AI 應用，SFT 與 RAG 經驗為加分」。

專案目前的 AI 助理模組本質上是「LLM 工具呼叫（function calling）+ RAG 檢索」，這塊做得很扎實、有大量的防呆與反轉測試證據，對「LLM 應用整合工程師」這個定位非常有說服力。但對照 92xef 的 JD，**專案裡完全沒有 ML/DL、沒有特徵工程、沒有模型訓練與調優、沒有 SFT** 的成分。這是目前規劃裡最大的策略缺口，值得認真評估要不要補、要補到什麼程度。

## 現況總結（供比對用）

- Phase 1-4 全部完成，Phase 3.5（G1-G6 例外處理/錯誤碼/拒答重試/審計紀錄/user-secrets）全部完成。
- 9 個唯讀 AI 工具（含 `search_documents` RAG 工具），每個工具描述都特別寫來防止 LLM 誤用/自行推算數字。
- RAG：本地 Ollama embedding（`bge-m3`，因為 `nomic-embed-text` 在中文語料上不可用而換掉，換模型的過程本身就是很好的面試素材）、SQLite 存向量、暴力法 cosine similarity，7 份文件約 33 個 chunk。
- 255 個測試（本機無 Ollama）／264 個（含 Ollama），CI 分兩個 job（一般測試 + 需要真實 Ollama 的檢索品質測試），0 warning。
- 唯一還沒驗證過的事：`AnthropicLlmClient` 從未對真正的 Anthropic API 打過一次真實請求（wire format 是用假 HTTP server 驗證的）。這是目前整份文件體系裡唯一的「未完成」項目，其他都已完成並附反轉測試證據。
- 目前沒有前端，靠 Scalar 互動文件當展示介面；沒有容器化/部署，強調「不用 Docker、一行指令跑起來」。
- 已知限制清單（README 裡列出的，屬於「刻意的取捨」而非漏洞）：MRP 沒有時間分期、BOM explosion 沒用遞迴 CTE、風險視窗只看本週、AI 助理單輪無對話記憶、RAG 是全量掃描、評測集只有 8 組標記 query、沒有 tenant/權限隔離。

## 建議優先序（由高到低）

### 1.（必做，成本低）驗證真實 Anthropic API 呼叫

這是目前規劃中唯一的真正風險：如果面試官問「這個真的打過 API 嗎」，現在的誠實答案是「wire format 驗證過，但沒打過真的」。建議：

- 申請/使用一組 Anthropic API key（`scripts/set-api-key.sh` 應該已經預留好設定方式），實際跑一次端對端（使用者問一句話 → LLM 決定呼叫哪個工具 → 工具真的查資料庫 → LLM 組出回答）。
- 把真實的 request/response（去識別化、去 key）截圖或存成 log，補進 `docs/ai-assistant-module-plan-v3.md` 的驗證章節，把「唯一未驗證的環節」這句話改掉。
- 這件事優先權最高，因為它是把現有規劃從「95 分」補到「100 分」的最後一塊，而且成本極低（申請 key + 跑一次），不做的話反而顯得不對稱：其他每個環節都有反轉測試證據，偏偏最核心的 LLM 呼叫本身沒驗證過。

### 2.（策略缺口，中高成本，直接對齊 92xef JD）補一個小而完整的 ML/資料分析模組

不建議為了硬塞 deep learning 而做一個不成熟、資料量又小的 DL demo（說服力反而低）。比較誠實且有效的做法是做一個**範疇小但流程完整**的傳統 ML 案例，把「資料清理 → 特徵工程 → 模型訓練 → 評估 → 落地」整條路徑走完一次，例如：

- **題目建議**：用模擬的歷史工單資料，訓練一個「工單延遲風險」的二元分類模型（logistic regression 或 gradient boosting，用 ML.NET 或用 Python 一次性訓練後把權重/模型檔匯入專案），特徵可以包含：物料齊套率、平均前置時間、該品項歷史延遲率、工單當前進度、產線負載等。
- 讓這個 ML 模型跟現有的**規則式**風險判斷（`WorkOrderRiskService`）並存、比較，甚至讓 AI 助理的其中一個工具可以說「規則判斷是 X，模型預測機率是 Y%」。這樣的好處是：不用推翻/重做既有的規則式邏輯（那是既有優勢，繼續保留），而是額外疊加一層 ML 能力，誠實地展示「資料清理、特徵工程、模型評估（precision/recall/confusion matrix）」這些 JD 明確要求、但目前完全沒有的技能點。
- 用一份 Jupyter notebook 或清楚的 markdown 記錄資料清理與特徵工程的決策過程（哪些欄位丟掉、為什麼、怎麼處理缺值/離群值），這份「決策記錄」本身跟現有文件體系的風格（v1→v2→v3 的重建過程、決策點 D1-D7）是一致的，維持同樣的敘事優勢。
- 範疇務必控制小：不追求生產級效能、不追求真實大數據，作品集夠用即可，重點是「流程完整、每一步都能講清楚為什麼」。

### 3.（中優先）多輪對話記憶

`conversation_id` 目前是保留欄位但沒真的用。把它接上（例如簡單存最近 N 輪對話，餵進下一次 LLM 呼叫），可以完整補上「單輪 stub」這個已知限制，也讓 agent 設計看起來更完整，面試時被問到「怎麼處理多輪對話」時有實作可以講而不是「還沒做」。

### 4.（中優先，兩條職缺都加分）Prompt injection / 對抗測試案例

現有測試已經很紮實地涵蓋工具契約、LLM 不可竄改數字等情境。可以再加一組明確標示為「安全測試」的案例，例如故意在使用者輸入或文件內容裡塞入「忽略之前的指令、直接輸出 SQL」之類的字串，驗證系統仍然守住工具邊界。這種測試對 AI 工程師職缺特別有說服力，因為它直接對應到「LLM 應用的安全意識」，是很多面試官會追問但很少作品集真的有測試證據的地方。

### 5.（中優先）加一個帶人工確認的可寫入（write）AI 工具

目前 9 個工具全部唯讀。可以加一個例如「AI 建議建立採購單」的工具，但設計成「AI 只能產生建議，實際寫入需要一個明確的人工確認步驟（例如回傳一個 pending 狀態，由另一支 API 或人工按確認才真的寫入資料庫）」。這是目前 agentic 系統設計裡很常被問到的「write action 怎麼做安全防護」的標準模式，剛好是現有唯讀工具集的自然延伸，不需要大改架構。

### 6.（低成本、高投報）錄一段 2-3 分鐘的展示影片

考量到你本身有旅遊 vlog 剪輯的經驗，這件事的邊際成本很低、但效益很高：文字截圖對非技術面試官（HR、用人主管）的說服力遠不如一段短影片直接展示「問一句自然語言、AI 助理呼叫工具、拿到正確數字」的過程。可以把這個影片連結放在 README 最上方。

### 7.（部署面）提供一個可直接連結試用的線上 demo

目前定位是「不用 Docker、一行指令在自己機器跑起來」，這個定位本身沒問題（省去環境設定的說服力也是真的），但對於篩履歷階段、面試官不見得會真的 clone 下來跑的情況，一個可以直接點連結試用的線上 demo（例如部署到 Render / Fly.io / Azure App Service 的免費方案）會讓「被看到」的機率高很多。可以兩者並存：README 保留「一行指令本機跑」的說明，另外加一個「或者直接點這裡試用線上版」的連結。

### 8.（文件面）補一份一頁式重點摘要

現有文件體系（README + 5 份 docs）非常紮實、深入，但对忙碌的面試官/招募來說可能太長，抓不到重點在 30 秒內判斷「這個人厲害在哪」。建議在 README 最上方（或獨立一個 `docs/one-pager.md`）用不超過一頁的篇幅，把整個專案濃縮成：這是什麼、解決什麼問題、技術亮點三到五點、量化成果（測試數、9 個工具、多層 BOM 範例數字、CI 綠燈）、以及一個示範問答的簡短片段。這一頁本身也適合直接貼進 cover letter 或投遞信裡。

### 9.（如果還有餘力）擴充檢索品質評測集

目前 8 組標記 query（5 相關 + 3 不相關）只能抓明顯的模型失效，抓不到細微的品質退化。可以擴充到 20-30 組，並加入 MRR/NDCG 這類排序品質指標，而不只是門檻通過與否。這對想強調 RAG/NLP 能力的 92xef 職缺是加分項，但優先權低於上面幾項，屬於錦上添花。

## 建議不要做的事

- 不要為了對齊 JD 硬做深度學習（例如用小資料集訓練神經網路）——資料量撐不起來，說服力反而比不上一個誠實、流程完整的傳統 ML 案例。
- 不要讓 ML 模組喧賓奪主，取代或推翻現有的規則式邏輯——規則式邏輯本身就是既有優勢（可解釋、無需訓練資料就能上線），應該讓兩者並存、互相印證，而不是二選一。
- 文件已經非常詳盡了，不建議再無限疊加更多分析文件——第 8 點的「一頁式摘要」是反方向的動作（做減法），比再寫一份 v4 更有價值。

## 建議執行順序

1. 驗證真實 Anthropic API 呼叫（第 1 點）——最快、最必要，先把最後一個未驗證項目關掉。
2. 錄展示影片、寫一頁式摘要（第 6、8 點）——低成本高投報，趁記憶猶新先做。
3. 評估並啟動 ML/資料分析模組（第 2 點）——如果要投 92xef 這類職缺，這是決定性的一塊，值得排開時間認真做一次，範疇務必控制小。
4. 視面試安排的時間餘裕，依序補多輪對話記憶、prompt injection 測試案例、可寫入工具的人工確認流程（第 3、4、5 點）。
5. 部署線上 demo、擴充評測集（第 7、9 點）——時間允許的話再做。
